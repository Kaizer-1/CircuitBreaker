# 0014 — GitOps Deployment with Argo CD

- **Status:** Accepted — amends [ADR-0007](0007-kubernetes-kind-and-helm-umbrella.md) (replaces its push-based CD
  with pull-based GitOps; kind, the namespaces and the umbrella chart stay). The agent-rollback part is amended by
  [ADR-0016](0016-rollback-reconciles-through-git.md) (the rollback now opens the `git revert` pull request itself)
- **Date:** 2026-11-03
- **Deciders:** Mohammad Oweis (owner, Release & Reliability Team), Kaizer Dewaswala, MD Asif Ali

## Context

ADR-0007 had GitHub Actions *push* releases into the cluster with `helm upgrade`. That has two problems:

1. GitHub's runners cannot reach a kind cluster on a student laptop, so "deploy to prod" in CI could only target a
   throw-away cluster inside the runner — not the cluster the audience sees.
2. The textbook's infrastructure (Mitra & Nadareishvili, Ch. 7) includes a **GitOps deployment server**, Argo CD,
   used by the **release team** (Ch. 2) to deploy microservices into production-like environments. Our design
   should match that infrastructure component.

> **GitOps:** a way of working where Git is the source of truth: whatever is in Git is the target state of the
> system, and a tool keeps the running system matching it and reports **drift** (live state that differs from Git)
> (Ch. 7). **Argo CD** is a GitOps tool for Kubernetes: it watches a Git path and *pulls* changes into the cluster.

## Decision

Adopt **Argo CD** as the GitOps deployment server, installed in the kind cluster (namespace `argocd`) by Terraform's
Helm provider, as in the textbook's `module-argo-cd` ([ADR-0015](0015-terraform-local-platform.md)).

**The flow:**

1. **GitHub Actions** (on merge to `main`): lint → test → build each changed service's image **once**, tagged with the
   git SHA → push to GHCR → **commit an image-tag bump** to `deploy/envs/staging/<service>.yaml`.
2. **Argo CD syncs `staging` automatically** when that commit lands. A PostSync hook Job runs the smoke tests inside
   the namespace.
3. **Promotion to `prod` is a commit too:** `make promote s=<service>` opens a pull request that copies the tested
   tag from `deploy/envs/staging/` to `deploy/envs/prod/`. The Release & Reliability Team approves it (CODEOWNERS on
   `deploy/envs/prod/`). Merging it is the release; Argo CD syncs `prod`.
4. **Release rollback = `git revert`** of the promotion commit; Argo CD syncs back.

**How Argo CD is configured:**

| Setting | Value | Why |
|---|---|---|
| Applications | One Argo CD `Application` **per service per environment**, generated by an `ApplicationSet`. Each renders the shared service sub-chart of the umbrella chart with `deploy/envs/<env>/<service>.yaml`. Data stores get their own Applications. | A commit for one service syncs only that service, so services deploy independently. |
| Automated sync | On, with `prune` | Git changes reach the cluster without anyone running `kubectl` or `helm`. |
| Self-heal | **Off** | With self-heal on, Argo CD would instantly undo *any* live change. It would undo the chaos experiment (so nothing would be left to heal) and the SRE agent's emergency rollback. With it off, Argo CD **reports** drift as `OutOfSync` but does not fight the agent. |
| Ignored differences | `spec.replicas` of Deployments, and the pod-template `restartedAt` annotation (with `RespectIgnoreDifferences=true`) | These fields belong to the SRE agent's `scale_deployment` and `restart_deployment` tools. Git doesn't own them, so a later sync must not reset them. |
| Polling | Every **30 s** (amended 2026-11-23, below; first: the default, about 3 minutes); `make sync` forces an immediate refresh in demos | A laptop cannot receive GitHub webhooks. |
| Repository access | Argo CD pulls from the GitHub repository (public, or a read-only deploy key stored as a Kubernetes Secret) | Pull means the cluster only needs *outbound* access to GitHub. That solves problem 1 above. |

**How Argo CD and the SRE agent work together:** the agent's four tools still act through the Kubernetes API (no new
tools — [ADR-0009](0009-sre-agent-fixed-tool-allowlist.md) is unchanged).

- **Scale and restart** only touch fields Argo CD ignores.
- **Rollback** after a chaos `BAD_DEPLOY` returns the Deployment to exactly what Git says, so the Application goes
  from `OutOfSync` back to `Synced`.
- **Rollback of a bad release that came through Git** is an emergency fix that leaves the Application `OutOfSync`.
  *Amended by [ADR-0016](0016-rollback-reconciles-through-git.md):* the rollback tool's own code then opens a
  `git revert` pull request. When a human merges it, Git and the cluster are back in line.

### Amendment (2026-11-23, owner's decision, Phase 6): poll every 30 seconds

Argo CD's default is to ask Git every 120 s plus up to 60 s of random jitter, so a commit waited up to 3 minutes
before anything happened. That is too slow to show "push → staging" live. Argo CD now polls every **30 s** with no
jitter (`timeout.reconciliation: 30s`, [infra/platform/argo-cd.yaml](../../infra/platform/argo-cd.yaml)); the measured
push-to-synced time is in the [deployment doc §4](../03-architecture/07-deployment-and-environments.md#4-cicd-pipeline-github-actions--argo-cd-gitops).
The cost is about 40 small Git fetches a minute from GitHub by the repo server, each answered from its cache unless
the commit changed. `make sync` stays, for "now". A webhook would remove the delay, but GitHub cannot reach a laptop.

The settings above are implemented in Terraform's `argo-cd` module (Phase 6): one `ApplicationSet` makes the
Applications `<service>-<env>` (13 per environment: 9 services, 3 data stores and the ingress), plus `secrets-<env>`
for the SealedSecrets ([ADR-0019](0019-sealed-secrets-for-gitops.md)) and `observability` for the dashboards and
alert rules. All belong to the AppProject `circuitbreaker`, which allows only this repository, only our namespaces
and **no cluster-wide objects**.

**Found while testing (2026-11-23): one Application per service was not enough.** With automated sync, Argo CD
re-synced **every** `OutOfSync` Application whenever **any** commit reached the branch, not only the Applications
whose files it changed. Measured on staging: order-service drifted by hand (as after the SRE agent's emergency
rollback), then a commit changed only web's values file, and Argo CD re-applied order-service from Git within a
minute. In production that would let an unrelated tag bump undo the agent's rollback before its `git revert` pull
request is merged ([ADR-0016](0016-rollback-reconciles-through-git.md)). Each Application now declares its own paths
(`argocd.argoproj.io/manifest-generate-paths`: the umbrella chart, `dev/`, its environment's `global.yaml` and its
own values file); a commit outside them updates the Application's revision without a sync. Re-tested: the drift
stayed through the unrelated commit (`make k8s-check c=gitops-push`). What remains, as ADR-0016 says: a commit to
the **same** service's file, or to the shared chart, re-applies Git.

**CI's half, as built (2026-11-24, Phase 6).** Step 1 of the flow above is `.github/workflows/ci.yml`; details and
reasons are in the [deployment doc §4, "CI as built"](../03-architecture/07-deployment-and-environments.md#ci-as-built-phase-6).
"Each changed service" is decided by comparing the service's folder (its build context) at the commit staging runs
with the new commit, so an unchanged service keeps its tag. Each image is scanned (Trivy) before it is pushed. The
tag bump writes the registry **and** the tag into the service's file, one commit per service, only after every CI job
passed. It pushes with a deploy key that `main`'s ruleset lets bypass the pull-request rule, and pushes that change
only `deploy/envs/**` do not start CI again.

**Found while testing (2026-11-24): too many syncs at once.** A commit that changed every service's pod template made
Argo CD start 18 syncs together; the application controller ran out of memory (768 MiB) and, resuming them on every
restart, stayed down for 20 minutes. It now runs at most 2 kubectl processes and 4 sync operations at a time (the
defaults are 20 and 10); the same syncs queue and finish in about a minute and a half. Because automated sync never
retries a revision it has attempted, `make sync apply=yes` starts the sync of Applications left `OutOfSync`, on
request only (an SRE-agent rollback can be `OutOfSync` on purpose).

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| **Push-based CD with `helm upgrade` from GitHub Actions** (ADR-0007's original choice) | Needs cluster credentials in CI and network access to the cluster; a laptop cluster is unreachable, so the real environment would be deployed by hand. Doesn't match the textbook's GitOps server. |
| **Flux** | Also a solid GitOps tool. Argo CD is the one the textbook uses (Ch. 7), and its web UI makes `Synced`/`OutOfSync` visible to an audience. |
| **One Argo CD Application per environment (the whole umbrella chart)** | Simpler, but any commit re-syncs every service. After an emergency rollback, an unrelated promotion would re-apply the bad release. |
| **Self-heal on** | Strongest drift control, but it would silently undo chaos experiments and the agent's fixes, so the self-healing demo would show the wrong healer. |
| **Give the SRE agent Git write access so it rolls back by commit** | Fully GitOps-pure, but a new and much broader power (it could change any file). ADR-0009 forbids widening the agent's tools. *(A much narrower form was later adopted in [ADR-0016](0016-rollback-reconciles-through-git.md): deterministic code inside `rollback_deployment` opens a revert **pull request** for one file and can never merge it.)* |

## Consequences

- ✅ Matches the textbook's infrastructure components: network → Kubernetes → **GitOps deployment server**.
- ✅ Every deploy and promotion is a reviewed Git commit. The audit trail is `git log deploy/`.
- ✅ The real demo cluster is deployed by the pipeline, with no manual `helm` or `kubectl`.
- ✅ Independent deployability holds in the deploy layer too: one Application per service.
- ✅ The approval step is a pull-request review, which fits the release team's responsibility of coordinating approvals (Ch. 2).
- ❌ One more component to run on a laptop (Argo CD uses roughly 0.5–1 GB of memory).
- ❌ Polling adds up to 30 s before a commit is noticed (amended 2026-11-23; ~3 minutes before), or a manual `make sync`.
- ❌ With self-heal off, manual drift persists until someone looks. The Argo CD UI and an `ArgoAppOutOfSync`
  dashboard panel make it visible.
- ❌ CI bot commits (tag bumps) add noise to `git log`. They are scoped to `deploy/` and excluded from the CI trigger
  to avoid loops.

## Viva Notes

**Q: What is GitOps, and how is it different from what you had before?**
A: Git holds the desired state and a tool in the cluster pulls it in and reports drift. Before, CI pushed releases
with `helm upgrade`. Now CI only builds images and commits a tag change; Argo CD deploys it.

**Q: Why does pull-based deployment suit a laptop cluster?**
A: The cluster only needs outbound access to GitHub. Push-based CD needs GitHub's runners to reach into the cluster,
which they can't for a laptop.

**Q: Doesn't Argo CD fight your SRE agent?**
A: No. Self-heal is off, and the fields the agent changes (replicas, restart annotation) are ignored. A rollback either
brings the cluster back to Git (after chaos) or is flagged as drift until a human reverts the bad commit.

**Q: How is a release promoted to prod?**
A: A pull request copies the tested image tag from the staging values file to the prod one. The Release & Reliability
Team approves it, and the merge is the release.

**Q: Which textbook component does this match?**
A: The GitOps deployment server from Chapter 7 (Argo CD), which the textbook's release team uses to deploy into
production and production-like environments.
